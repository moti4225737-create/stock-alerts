# נהלי העבודה המחייבים

מסמך זה מרכז את כללי העבודה המחייבים לניהול התיעוד והארכיון.

הוא אינו פרוטוקול הסגירה העליון של Stock Sentinel.

כל שינוי מהותי, כולל שינוי תיעוד או Governance, כפוף לפרוטוקול הסמכותי שב־:

`../03-ניהול-הפיתוח-ההנדסי/פרוטוקול-השינוי-האימות-המסירה-והסגירה-הסמכותי.md`

## מתודת הכרעה

בהחלטה תיעודית מהותית או עמומה עובדים לפי הסדר:

1. מהות ומטרה.
2. מיפוי התהליך המעשי.
3. בדיקת תרחיש תקין.
4. בדיקת תרחיש כשל, שימוש לרעה או סיכון כאשר רלוונטי.
5. בדיקה מזווית נוספת ובדיקה חוזרת.
6. Benchmark מקצועי חיצוני כאשר הוא יכול לשפר את ההחלטה.
7. הצעה מנומקת.
8. החלטת בעל המוצר.
9. קיבוע ה־Current Truth והנימוק ההיסטורי.

## כלל סמכות

המאגר הממומש הוא האמת התפעולית לגבי מה שקיים בפועל.

הארכיון מתעד את המצב המאומת, ההחלטות, המטרות והכיוון המאושר.

החוקה שומרת רק את גרעין העקרונות שאינו אמור להשתנות עם המימוש.

הפרוטוקול ההנדסי הסמכותי הוא ה־Closure Authority היחיד למחזור שינוי End-to-End.

## Natural Home

לכל מידע סמכותי יש בית טבעי אחד.

כאשר פרט שייך לתחום Product, Architecture, Engineering, Operations, QA או Knowledge Governance, תוכנו המקצועי נשמר בבית המתאים.

הפרוטוקול הסמכותי מפנה לבתי הסמכות ואינו מצדיק שכפול מידע.

## אישור

מיפוי, Classification, שינוי מבני, שינוי Authoritative Ownership או שינוי מהותי בתיעוד אינם הופכים לסופיים ללא אישור בעל המוצר.

## Documentation Checkpoint

Documentation Checkpoint הוא בקרה פנימית מחייבת בפרוטוקול העליון.

הוא כולל:

- Documentation Impact Map;
- Current Truth;
- Chronicle;
- Traceability;
- Evolution כאשר רלוונטי;
- Access / Disclosure כאשר רלוונטי;
- Final Documentation Review.

Completion של Documentation Checkpoint אינו לבדו Closure של ספרינט או שלב.

## שמירת רצף

שיחות עבודה הן סביבת עבודה ולא Repository.

החלטה מהותית שאושרה חייבת להגיע לבית הסמכותי המתאים בארכיון ולא להישאר תלויה בזיכרון שיחה.

כאשר תהליך עבודה מגלה שמידע או כלל כמעט נשכחו, אין להסתפק בזכירתם להבא.

יש לבדוק האם הפער שייך לפרוטוקול הסמכותי, ואם כן לעדכן את הפרוטוקול כך שהפער לא יוכל לעבור שוב Closure בלי להיתפס.

פתיחה, רישום ו־Handoff של יחידות R&D ושיחות עבודה כפופים ל־`R&D Unit and
Conversation Continuity Protocol — נוהל רציפות יחידות R&D ושיחות עבודה`
שב־`../03-ניהול-הפיתוח-ההנדסי/ניהול-ספרינטים.md`. נוהל זה שומר רציפות
ומספק ראיות לפרוטוקול הסמכותי; הוא אינו Gate או Closure Authority.

## גידור מחדש וטעינת מקורות סמכותיים

At these triggers invoke the repository Design C resolver, consume the actual
applicable authority and reconstruct station/obligations from their durable homes.
Before any station/consequential transition invoke its transition mode. The
contract is owned by `../03-ניהול-הפיתוח-ההנדסי/החלטות-הנדסיות.md`.
Known material outcomes must reach their existing Natural Homes at this station;
UNRESOLVED_CLASSIFICATION or missing persistence prevents its completion.
An OPEN obligation due later is carried, not automatically a blocker of earlier
legitimate work. Invocation remains an agent duty unless technically mediated;
never call the instruction itself hard enforcement.

Opening של יחידת R&D, ‏First-Minute Re-grounding ו־Final Re-grounding טוענים
מחדש במלואם את נהלי העבודה המחייבים הישימים ואת המקורות הסמכותיים שאליהם הם
מפנים; אין להסתמך על זיכרון, summary או Handoff בלבד.

מילת ההפעלה `הפסקה` מחייבת אותה טעינה וגידור מחדש מיידיים. אותה בקרה מופעלת
אוטומטית כאשר מתגלה Grounding Loss או drift מהותי בין הפעולה המתוכננת לבין
המטרה, ה־scope, ה־contract, ההחלטות, האישורים, הפעולות האסורות, המצב החיצוני
או מצב המאגר הסמכותי.

הבדיקה משווה את המצב הנוכחי למקורות הסמכותיים ומחזירה בדיוק אחת מן התוצאות:

- `גידור מחדש — PASS` — המצב והפעולה הבאה תואמים לראיות, לסמכות ולאישורים;
- `גידור מחדש — STOP` — קיימת סתירה, חסרה ראיה או נדרשת החלטה/הרשאה.

## איפוס ממסר לפני מנגנון חדש

כאשר העבודה עומדת להמציא, לבנות או להוסיף מנגנון תפעולי חסר, integration,
linking layer או bridge טכני חדש, מופעל אוטומטית או באמצעות מילת ההפעלה
`ממסר` רצף הבדיקה הבא לפני Impact Map של המנגנון:

real missing product function
→ existing internal primitives / adapters / tools
→ analogous external systems
→ Build / Buy / Adapt / AI
→ עד שלוש חלופות
→ evidence / assumptions / complexity / dependency / cost / risk
→ הוכחת התאמת המנגנון לבעיה
→ minimum Sentinel glue
→ Product Owner decision
→ Impact Map
→ Contract / RED / implementation.

הבדיקה אינה מחליפה Impact Map ואינה סמכות Architecture חדשה. תוצאתה היא:

- `איפוס ממסר — PASS`; או
- `איפוס ממסר — STOP`.

## עצירה בסטייה מהותית

כאשר ראיה בפועל סוטה מהותית מן ה־plan, contract, scope, mechanism,
architecture, dependency assumption או migration/removal order שאושרו:

STOP מיידי
→ דיווח הראיה והסטייה המדויקות
→ החלטת Product Owner
→ resume או replan רק לאחר ההחלטה.

עד אז אין ליצור RED חדש, לבצע GREEN, להוסיף compatibility repair אוטומטי או
לבצע תיקון שמשנה scope. legacy debt ממופה שמופיע בדיוק כמאושר אינו deviation.
בעיית runner או permission תפעולית טהורה שאינה משנה את המנגנון המאושר אינה
כשלעצמה deviation ארכיטקטוני.

## Product Goal ו־Minimum Proven Surface

לפני הוספת מורכבות חוזרים למטרת המוצר שבחוקה ולמטרה המאושרת הנוכחית, ובודקים
אם העבודה משפרת מהותית את יכולת ה־investment decision support או נדרשת
לאמינות, בטיחות ויכולת התפתחות. עובדים לפי `תהליך-הפיתוח.md`: מעדיפים את
הפתרון הקטן והנכון ביותר, מרחיבים primitives ומבנים קיימים לפני מסלול מקביל,
ובפתרון blocker ב־Alpha פועלים על minimum proven surface בלי מורכבות
ספקולטיבית, תוך שמירת extensibility עתידית.

### Orientation Before Direction Change

Before recommending or performing an action that changes work direction, changes
work state, or creates a consequence — through ChatGPT, Terminal, Codex, another
tool, or conversation itself — the Agent must raise its view above the local
problem and connect:

NEAR-TERM GOAL
→ CURRENT AUTHORITATIVE STATE
→ LONG-TERM PRODUCT GOAL
→ PROPOSED ACTION

Technical possibility or solving the local/micro problem is not sufficient grounds
for recommending an action. The action must be the shortest safe action appropriate
to the current authoritative state and the near- and long-term goals. If this
connection is materially unclear, the Agent must surface the ambiguity to the
Product Owner rather than invent new work or advance automatically.

This is an Orientation rule within the single Authoritative Change, Validation,
Delivery and Closure Protocol. It creates no Gate, classifier, router, traffic-light
system, decision authority, registry, lifecycle, workflow or process tree, and
does not promise zero Agent errors. Technical enforcement at observable execution
boundaries, where practical and actually proven, is complementary protection;
it does not solve semantic Orientation.

## משמעת אינטראקציה וביצוע

כאשר ניתנות הוראות ביצוע מונחה, משמעות התוויות היא:

- `להדביק ל־Codex` — להעביר ל־Codex כהוראת עבודה;
- `להריץ ב־PowerShell` — המשתמש מריץ את הפקודה ב־PowerShell;
- `לעיון/אישור בלבד` — תוכן לעיון או להחלטה בלבד; אין לבצע אותו.

עברית בהירה וקריאה היא convention של שכבת האינטראקציה בלבד ואינה Gate או
Closure Authority. פרטי UI זמניים, נתיבי executable מקומיים ונוסח approval
dialog אינם Governance קבוע.

לאחר ששלב בטוח הצליח, ממשיכים מיד לפעולה הבאה הניתנת לביצוע והנכונה לפי
הפרוטוקול, בלי להמתין לכך שה־Product Owner יכתוב "continue", "task?" או
ניסוח מקביל. עוצרים רק כאשר הפעולה הבאה תלויה בראיית משתמש, בהחלטת Product
Owner, ב־dependency או אי־ודאות מהותיים, באישור מפורש לפעולה משנה־מצב או
consequential, או בתנאי STOP מחייב.

ברירת המחדל של הוראת ביצוע למשתמש היא יחידת הביצוע הבטוחה המקסימלית שמגיעה
עד נקודת ההחלטה או התלות האמיתית הבאה. כאשר כמה READs, בדיקות או פעולות
בטוחות משרתים אותה הכרעה והמשך הביצוע ביניהם אינו תלוי בתוצאת ביניים, יש
לאחד אותם ליחידת ביצוע אחת. אין לפצל עבודה ל־micro-steps רק כדי לצפות
בתוצאות ביניים.

פיצול או עצירה מותרים כאשר תוצאת ביניים עשויה לשנות את הפעולה הבאה, קיימים
סיכון לנזק או לחשיפת מידע, נדרשת החלטת Product Owner, נדרש אישור מפורש
לפעולה משנה־מצב/consequential, קיימת dependency או אי־ודאות מהותית, או חל
STOP boundary מחייב. "פעולה אחת בכל פעם" פירושה execution unit בטוח אחד,
ולא בהכרח command יחיד. כלל זה הוא ברירת מחדל רציפה ואינו תלוי בהפעלת
"הפסקה"; "הפסקה" היא recovery/re-grounding control בלבד.
