# ניהול ספרינטים

ספרינט הוא יחידת עבודה ממוקדת בעלת מטרה ברורה, Scope מוגדר ו־Exit State שניתן לאמת.

## סמכות סגירה

ספרינט או שלב רשמי כפופים ל־:

`פרוטוקול-השינוי-האימות-המסירה-והסגירה-הסמכותי.md`

Definition of Done של ספרינט הוא דרישה פנימית בפרוטוקול הסמכותי ואינו Closure Authority נפרד.

## משמעת Scope

אין לפתוח מסלול עבודה חדש במהלך ספרינט אלא אם מתגלה:

- Crash;
- טעות מהותית;
- סיכון Production מהותי;
- בעיה ארכיטקטונית המחייבת טיפול;
- או חסם שמונע את השגת מטרת הספרינט.

ממצא חשוב שאינו מחייב עצירה נרשם להמשך ואינו משתלט על הספרינט הפעיל.

## Definition of Done

בתוך הפרוטוקול הסמכותי נדרש לפחות:

- הערך שנקבע לספרינט סופק;
- ה־Scope נשמר;
- הבדיקות הממוקדות עברו;
- Full Regression עבר;
- השינוי נבדק;
- Commit ו־Push עברו את הבקרות והאישורים הרלוונטיים;
- Branch / CI / Deployment / Runtime validations עברו כאשר הם רלוונטיים;
- המאגר נשאר במצב ידוע ונקי;
- בוצע Documentation Checkpoint.

גם עמידה ברשימה זו אינה עוקפת דרישה רלוונטית אחרת בפרוטוקול הסמכותי.

## Documentation Checkpoint

סיום ספרינט משמעותי כולל כחלק מהפרוטוקול:

1. Current Truth — עדכון המצב התקף בארכיון.
2. Chronicle — תיעוד מתי, למה וכיצד השתנה המוצר.
3. Traceability — חיבור למסמכים, בדיקות, החלטות, Commit / Tag / Version והראיות הרלוונטיות.

## R&D Unit and Conversation Continuity Protocol

### נוהל רציפות יחידות R&D ושיחות עבודה

נוהל זה הוא פרוטוקול תפעולי כפוף לניהול יחידות R&D ולרציפות בין שיחות
עבודה. הוא אינו Closure Gate, אינו סמכות חלופית ואינו מחליף את
`פרוטוקול-השינוי-האימות-המסירה-והסגירה-הסמכותי.md`.

הנוהל מספק הקשר וראיות לפרוטוקול הסגירה הסמכותי היחיד. רק הפרוטוקול
הסמכותי רשאי לקבוע Closure של ספרינט או שלב רשמי. סיום שיחה והשלמת Handoff
אינם כשלעצמם Closure.

### זיהוי ומספור

- המזהה הקנוני הוא `R&D NNN`.
- המספור הוא תלת־ספרתי, רציף וכלל־מאגרי.
- מזהה שהוקצה הוא immutable ואינו ניתן לשימוש חוזר.
- כותרת יחידה נכתבת בתבנית `R&D NNN — Title`.
- שם קובץ Chronicle עתידי נכתב בתבנית
  `YYYY-MM-DD-rnd-NNN-<short-slug>.md`.
- לכל יחידה נרשמים predecessor ו־successor כאשר הם קיימים.
- `NEXT` מציין יחידה רשומה שטרם נפתחה; אין להציג אותה כ־`OPEN` לפני פתיחה
  מפורשת.

### Opening Block מחייב

כל שיחה הפותחת יחידת R&D מתחילה בבלוק הבא, המועתק מן המידע הסמכותי
העדכני ולא מזיכרון השיחה הקודמת:

ה־Opening Block הוא continuity bootstrap: הוא טוען את הקשר ה־Handoff ואת
ההפניות לבתי הסמכות, אך אינו מקור אמת עצמאי ואינו ראיה שהמצב שירש עדיין
תקף. לפני consequential work נדרשים טעינת המקורות המחייבים הישימים ו־
First-Minute Re-grounding לפי `נהלי-העבודה-המחייבים.md`.

```text
R&D ID:
Title:
Status:
Predecessor:
Authoritative handoff:

Current objective:
Approved scope:
Explicitly deferred / out of scope:

Carried Current Truth:
Authoritative prior decisions / contracts:

Safety and Production state:
Forbidden actions:
External-state verification required:

Repository baseline:
- branch
- Product Implementation SHA
- Governance / Documentation evidence
- Pre-Commit Local HEAD
- Final / Handoff commit, or `FINAL / HANDOFF COMMIT: PENDING`
- authoritative pushed SHA, when one exists
- deployed SHA, when applicable
- upstream
- working-tree state
- protected local files

Validation / evidence baseline:
Causal State Bridge:
- STATE BEFORE
- TRANSITION / EVENT / PRODUCT OWNER DECISION
- EVIDENCE
- STATE AFTER
- REMAINDER
- NEXT OWNER / STATION
Open work:
Known risks / real-world unknowns:

Required cadence / governing protocol references:

Required end-of-conversation handoff:
- achieved state
- evidence
- unresolved / deferred work
- repository state
- Production / external state
- successor R&D unit
```

### Working Cadence

ה־Opening Block אינו משכפל הוראות עבודה. יחידת R&D מפנה לפרוטוקול השינוי,
האימות, המסירה והסגירה הסמכותי, למסמכי ה־TDD, ל־Documentation Checkpoint
ולבתי הסמכות התחומיים החלים עליה. ה־Scope, פעולות אסורות, אישורי Product
Owner וגבולות Production / external systems נשמרים לאורך השיחה.

### Causal continuity and obligation classification

ה־Opening Block וה־Handoff חייבים לאפשר להבין את הרצף הבא בלי לנחש:

STATE BEFORE
→ TRANSITION / EVENT / PRODUCT OWNER DECISION
→ EVIDENCE
→ STATE AFTER
→ INTENTIONALLY OPEN / BLOCKED / CARRIED / DEFERRED REMAINDER
→ NEXT OWNER / STATION.

לכל obligation שנותר ניתנת disposition אחת בלבד:

- `COMPLETED`;
- `INTENTIONALLY OPEN`;
- `BLOCKED`;
- `CARRIED`;
- `DEFERRED`;
- `EXPECTED DOCUMENTATION / CLOSURE-EVIDENCE GAP`;
- `PROVEN DEVIATION`;
- `DROPPED OBLIGATION`, רק כאשר הוכח שהחובה בוטלה כדין.

הסיווג כולל owner או next station, prerequisite, ראיה קיימת וסיבה כאשר
הפריט אינו `COMPLETED`. הוא אינו משנה את זהות ה־Gate או מעניק Closure.

### Final Historical / Causal Reconstruction

לפני יצירה או סיום של Authoritative Handoff מבוצע:

`FINAL HISTORICAL / CAUSAL RECONSTRUCTION — READ / ANALYSIS ONLY`.

השחזור משתמש במקורות הסמכותיים ובראיות המאגר ומציג:

STATE
→ TRANSITION / DECISION
→ EVIDENCE
→ NEW STATE
→ REMAINDER
→ NEXT OWNER / STATION.

הוא מבחין במפורש בין עבודה שהושלמה, עבודה שנותרה בכוונה `OPEN`, prerequisites
חסומים, עבודה `CARRIED`, עבודה `DEFERRED`, פערי documentation/closure-evidence
צפויים, deviations מוכחים וחובות שהוכח כי בוטלו. ה־Handoff הסופי נוצר רק מן
המצב הסופי המאומת ומן השחזור הזה.

### Governance Delta Check and Accumulated Delta Sweep

לפני Final Re-grounding מבוצע Governance Delta Check: נבדק אם העבודה יצרה,
שינתה, חיזקה או הבהירה כלל עבודה או Governance קבוע. כלל reusable אינו נשאר
רק בזיכרון שיחה, Handoff, Chronicle, Current Truth או Traceability, אלא מגיע
ל־Natural Home שלו. אירוע חד־פעמי אינו הופך אוטומטית לכלל קבוע.

באותה תחנה מבוצע `Accumulated Delta Sweep` על כלל השינוי המצטבר מאז baseline
הכניסה הסמכותי או continuity checkpoint ישים אחרון, ולא רק על `git diff`.
הוא כולל, כאשר ישים: החלטות ואישורי Product Owner; שינויי product,
architecture ו־domain contract; שינויי Current/operational truth; תוצאות
implementation ו־validation; שינויי proof/evidence; חובות `OPEN`, `BLOCKED`,
`CARRIED` ו־`DEFERRED`; סיכונים, unknowns ופערים צפויים; deviations והכרעתם;
חובות documentation ו־traceability; שינויי governance/process/enforcement;
החלטות הקיימות רק בשיחה הפעילה; ראיות חיצוניות או consequential; ו־successor
ownership ו־prerequisites.

כל delta מהותי מקבל disposition אחת:

- `ALREADY ANCHORED`;
- `UPDATE NATURAL HOME`;
- `UPDATE CURRENT TRUTH`;
- `UPDATE CHRONICLE`;
- `UPDATE TRACEABILITY`;
- `UPDATE R&D REGISTER / HANDOFF`;
- `CARRIED — OWNER / NEXT STATION DEFINED`;
- `DEFERRED — APPROVED REASON / OWNER OR TRIGGER DEFINED`;
- `NOT APPLICABLE — REASON RECORDED`.

כאשר delta אחד משפיע כדין על כמה רשומות, נשמר owner סמכותי ראשי אחד והיתר
מסווגות כ־synchronization או cross-reference. התוצאה היא בדיוק:

`ACCUMULATED DELTA SWEEP — PASS`

או:

`ACCUMULATED DELTA SWEEP — STOP`.

אין להתקדם לסגירה כאשר delta מהותי חסר disposition, destination או owner,
כאשר סמכותו עמומה, כאשר קיימים duplicate authority או instance leakage
מהותיים, או כאשר נדרשת החלטת Product Owner שטרם התקבלה.

שינוי Governance קבוע מתאר roles, states, transitions, triggers, invariants,
responsibilities, evidence semantics ו־validation באופן כללי. הוא אינו מקודד
בטעות מספר יחידת R&D מסוים, SHA נוכחי, תאריך נוכחי, carried item נוכחי או
incident state נוכחי, אלא אם המזהה הוא במכוון חלק מן התקן הקבוע. עובדות instance
שייכות לרשומות state/evidence/continuity. לפני Pre-Commit Continuity נדרש:

`GENERICITY / INSTANCE-LEAK — PASS`.

### Final Re-grounding and Pre-Commit Continuity

לאחר Documentation synchronization, ‏Governance Delta Check ו־Accumulated
Delta Sweep, ולפני סיום ה־Authoritative Handoff, מבוצע Final Re-grounding מלא
לפי `נהלי-העבודה-המחייבים.md`. רק `גידור מחדש — PASS` מאפשר להמשיך.

לפני ה־closing/Handoff commit מבוצע `PRE-COMMIT CONTINUITY CHECKPOINT`.
הוא מאמת שהרשומות הישימות מסונכרנות: Chronicle, ‏Current Truth,
Traceability, ‏R&D Register, ‏Handoff וכל Natural Home של Governance delta
ישים; שה־Genericity check עבר; ושאין שינוי מאושר שנותר רק בזיכרון השיחה.

אין לנבא SHA של commit שטרם נוצר. לפני יצירת closing/Handoff commit נכתב:

`FINAL / HANDOFF COMMIT: PENDING`.

ה־SHA שנוצר הופך לאחר מכן לראיית repository דרך מנגנון ה־closure-evidence,
Traceability וה־late-evidence/write-back הקיימים.

### Continuity Comprehension Acceptance Criterion

successor שאין לו זיכרון אישי של השיחה הקודמת חייב להיות מסוגל, באמצעות
Opening/Handoff והמקורות הסמכותיים הנוכחיים, לקבוע בלי לנחש: מהו המוצר; מהי
המטרה המאושרת; מהי התחנה המדויקת; כיצד הגיע המצב אליה; מה הושלם; מה נשאר
ולמה; מה `BLOCKED`, ‏`CARRIED` או `DEFERRED`; איזו ראיה תומכת בכל מצב מהותי;
מי owner של כל המשך; מהם ה־prerequisites; ומהי הפעולה המותרת הבאה. אם קשר
מהותי בין status, evidence, cause ו־owner דורש ניחוש, continuity validation
אינו `PASS`.

### End-of-Conversation Handoff

לפני סיום שיחה נרשמים ב־Chronicle או בבית הסמכותי המתאים:

- המצב שהושג והראיות התומכות בו;
- מה לא הושלם, מה לא הוכח ומה נדחה במפורש;
- מצב branch, ‏HEAD, upstream, working tree ופעולות Git שטרם בוצעו;
- מצב Production ושירותים חיצוניים, כולל `NOT VERIFIED` כאשר אין ראיה חיה;
- החלטות וחוזים שנותרים סמכותיים;
- מזהה היחידה הבאה ומעמדה;
- הפעולה הראשונה המומלצת ביחידה הבאה.

Handoff סוגר את רציפות השיחה בלבד. סטטוס היחידה ב־R&D Register וסטטוס
Closure לפי הפרוטוקול הסמכותי נרשמים בנפרד ואסור להסיק אחד מן האחר.

סדר הרציפות המחייב הוא:

AUTHORITATIVE OPENING BLOCK
→ FIRST-MINUTE RE-GROUNDING
→ VERIFIED ENTRY STATE
→ APPROVED R&D WORK
→ EVIDENCE / VALIDATION
→ FINAL HISTORICAL / CAUSAL RECONSTRUCTION
→ CLASSIFICATION OF ALL REMAINING OBLIGATIONS
→ DOCUMENTATION / GOVERNANCE DELTA CHECKPOINT
→ FINAL RE-GROUNDING
→ AUTHORITATIVE HANDOFF
→ PRE-COMMIT CONTINUITY CHECK
→ APPROVED CLOSING COMMIT
→ SUCCESSOR OPENING BLOCK
→ SUCCESSOR RE-GROUNDING.

ה־Handoff וה־Opening Block מסבירים כיצד הגענו למצב המועבר. ה־First-Minute
Re-grounding של ה־successor קובע אם אותו מצב עדיין נכון כעת. אף אחד מהם אינו
מחליף את בתי האמת הסמכותיים או את ה־Closure Gate היחיד.

### OPEN-GATE Handoff

יחידת R&D או שיחת העבודה שלה רשאית להגיע למצב `CLOSED — HANDED OFF` כאשר
ה־Closure Gate הסמכותי היחיד עדיין `OPEN`, רק אם התוצאה המאושרת של היחידה
הושלמה עד הגבול שהוגדר וכל תנאי הרציפות הבאים מתקיימים:

- כל control שנותר `OPEN` או `BLOCKED` מתועד ב־Handoff עם זהות ה־Gate
  המקורית שלו, סטטוס נוכחי, ראיות שכבר הושגו, סיבת הפתיחה או החסימה,
  prerequisite להשלמה וכל אישור או תנאי בטיחות נדרש;
- successor יחיד מקבל בעלות מפורשת על ה־controls הנישאים;
- ה־Handoff אינו מוותר, סוגר, מחליף או מסווג מחדש control כלשהו;
- ה־Opening Block או First-Minute Re-grounding של ה־successor חייבים לאשר
  במפורש את ה־controls הנישאים לפני consequential work;
- הרשאה ל־push, deployment, Production, runtime או פעולה חיצונית אחרת אינה
  עוברת בירושה מן היחידה הקודמת;
- לאחר השגת הראיות החסרות מעדכנים את Chronicle / closure record של היחידה
  הקודמת ואת ה־R&D Register, ‏Current Truth ו־Traceability לפי הצורך,
  ומעריכים מחדש את אותו Gate סמכותי;
- Gate עובר ל־`PASS` רק אם כל ה־controls החלים עברו בפועל;
- השלמת Gate מאוחרת אינה פותחת מחדש או מרחיבה את scope המימוש שהושלם ביחידה
  הקודמת.

מצב `CLOSED — HANDED OFF` מתאר את יחידת העבודה והשיחה בלבד. הוא אינו
`Closure Gate PASS`, ועדיין קיים Closure Gate סמכותי אחד בלבד.
