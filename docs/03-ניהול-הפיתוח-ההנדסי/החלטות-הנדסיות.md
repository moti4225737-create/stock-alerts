# קבלת החלטות הנדסיות

החלטות משמעותיות מתקבלות רק לאחר הבנת ההשפעה המלאה על המערכת.

## סדר עבודה מחייב

1. מגדירים את מהות המטרה והבעיה.
2. מבצעים End-to-End Impact Map של המערכת הקיימת.
3. מזהים Producers, Consumers, Orchestrators, Runtime integration points, fallbacks, tests ויישומים מקבילים או legacy.
4. בוחנים את התהליך המעשי שההחלטה צריכה לשרת.
5. בודקים תרחיש תקין ותרחיש כשל או ניצול לרעה כאשר רלוונטי.
6. מבצעים בדיקה מזווית נוספת ובדיקה חוזרת בהחלטות מהותיות.
7. מבצעים Benchmark מקצועי חיצוני כאשר הוא יכול לאתגר או לאמת את ההחלטה.
8. מוצגת הצעה מנומקת.
9. בעל המוצר מחליט.
10. רק לאחר האישור מתחילים RED או שינוי Domain Contract / Architecture.

## כלל מיפוי

אין לקבל החלטה על בסיס ענף חלקי של המערכת.

מטרת ה־Impact Map היא למנוע שכפול אחריות, ארכיטקטורה היברידית, תלות נסתרת ושינוי שמטפל בחלק אחד תוך שבירת צרכן אחר.

## Lean Design C — binding and transition support

This is an internal supporting control of the existing Authoritative Change,
Validation, Delivery and Closure Protocol. It does not authorize product
decisions, execute actions, or grant Closure PASS.

Authority → binding → applicability → durable obligation → transition check
→ required proof → evidence → the existing authoritative protocol.

`decision-bindings.json` links stable IDs to authoritative paths/headings and
UTF-8 text digests (CRLF normalized to LF). The current implementation pins the
whole referenced document, conservatively invalidating bindings on any change.
It never copies the normative decision into the binding. Components contain
explicit paths/consumers; diagnosis without paths loads the small baseline set.
Unknown changed scope is unresolved. Known provider composition is inspected
without importing runtime code; dynamic dependencies still require review.

`open-obligations.json` is the single current status location for carried
requirements. It is not a backlog, Chronicle, Current Truth or new Gate.
OPEN becomes CLOSED only with matching proof artifacts and validated receipts.
Missing evidence, wrong proof class/scope/action, changed proof bytes or broken
references cannot satisfy a requirement. SUPERSEDED/NOT_APPLICABLE require an
approved disposition in the existing evidence home; silent deletion is invalid.
Proof levels keep the exact meaning defined in §17 of the governing protocol.

`obligation-coverage-baseline.json` preserves approved coverage identities, not
current statuses. The caller supplies an independently approved SHA-256 pin.
Before the first approved commit the PO-approved initial sample is the bootstrap
baseline. After commit, compare against that explicit approved Git version.
Never refresh a pin or rewrite a baseline simply to make validation pass.
Changing the baseline and checker together remains a trust/review boundary.

## Required-before transitions

PRE_COMMIT and PRE_PUSH_OR_PROMOTION map to the existing repository/delivery
stations. PRE_CANARY and PRE_PRODUCTION consume the applicable preactivation
requirements. PRE_EXTERNAL_WORK validates bounds/permission before external
consequence, including Opening. PRE_CLOSURE consumes applicable closure proof.
These are transition boundaries, not additional Gates. FOUNDATION_GREEN checks
the foundation's own acceptance obligations; STATION_COMPLETE checks persistence.

The approved initial carried sample has these earliest applicable boundaries:
- #21/#22/#26: PRE_CANARY or direct PRE_PRODUCTION of the same path.
- #28: PRE_EXTERNAL_WORK, also consumed by activation.
- C2/X1: PRE_CANARY / PRE_PRODUCTION preactivation.
- X2: POST_PUSH release-delivery proof for the actual authorized Push of Release
  Subject R: authoritative remote SHA, exact intended-R CI and CI PASS produce
  valid X2 delivery evidence. X2 remains OPEN until that proof is validated.
  Fresh Forward Consequence / delivery-coupling evidence remains PRE_PUSH
  (PRE_PUSH_OR_PROMOTION), safeguarding the Push with explicit Push authorization;
  it does not consume the X2 delivery proof that the authorized Push creates.
  PRE_CLOSURE requires X2 and all applicable controls satisfied. A direct deployment
  also requires the applicable fresh Forward Consequence Check.
- X3: PRE_CLOSURE for the applicable real Canary outcome.

Earlier local diagnosis is not blocked solely by future OPEN obligations.
Direct activation cannot bypass its cumulative prerequisites. Future X3 proof
must not be required before the Canary that produces it. Prior action evidence
does not authorize a new action; current explicit PO approvals remain mandatory.

### Controlled Renewal

Controlled Renewal is an internal evidence-lifecycle transition of Lean Design C,
not a Gate, authorization source or Closure Authority.

After the approved initial bootstrap, when a changed subject makes previously
valid evidence stale, renewal is eligible only when all of the following are
proven together:

- existing applicable Authority / Binding;
- explicit approved change scope;
- current station / decision authorization for that scope.

A valid receipt may declare a dependency outside its owning component's paths
when that dependency is materially relevant to its claim or acceptance boundary.
When an already-declared dependency changes, owning-component path membership
alone must not prevent entry into this existing Controlled Renewal lifecycle.
Supplying an arbitrary filename does not establish a declared evidence dependency
or renewal eligibility. Existing authority, station/scope, approval/action and
independent-blocker controls remain required. Component paths retain their
ownership, scope, impact-mapping and implementation-authorization roles.

An eligible stale proof is classified `RENEWAL_REQUIRED`. This classification is
not PASS, does not make stale evidence valid and does not authorize the change.
Fresh required proof must pass before renewed evidence becomes active. Prior
receipts and artifacts remain preserved as history.

DEPENDENCY determines invalidation. ACTUAL IMPACT / APPLICABILITY determines
the validation required for renewal. A changed declared dependency makes the
existing receipt invalid and non-consumable under unchanged fail-closed proof
validity. Entry does not establish applicability, artifact reuse, validation
sufficiency, obligation satisfaction or transition permission.

Before completion, fresh applicability determination must establish the effect
of the changed dependency on the specific CLAIM + ACCEPTANCE BOUNDARY and
materially affected dependencies/interactions. Historical disposition is not
current validation. An existing historical validation artifact may be reused
as input to a new immutable receipt only when continued applicability is
established without requiring replay. If focused validation is required, the
minimum relevant focused validation must pass. If a narrower boundary cannot
establish applicability, broader applicable validation is required. Unresolved
required applicability remains fail-closed at the dependent acceptance boundary.
Neither automatic artifact reuse nor blanket replay follows from a byte change.
Historical receipts remain immutable; renewal does not rewrite their subjects
or claims. Applicability determination remains within the existing trusted
validation/review boundary, not automated semantic adjudication by the Resolver.

Unknown, unbound, unresolved, out-of-scope or unapproved change remains
fail-closed. Filename-based historical whitelists are not renewal authority.

The lifecycle is:

`VALID → STALE → RENEWAL_REQUIRED → VALID / BLOCKED`.

A `BOUNDED_INTERMEDIATE_GREEN` request in resolve mode may receive explicit
intermediate implementation permission only with existing applicable authority
and binding, an ACTIVE applicable station, complete requested-scope coverage
by bound components and station scope, and separate matching PO authorization
for that GREEN action. Existing approval checks apply to issuer, action,
action_id, scope, candidate/provenance and station approval reference; the
approval's change scope must cover the entire requested implementation scope.
Design C evaluates that existing PO authorization; it does not create Product
Owner authority. RED authorization alone does not authorize GREEN.

Eligible subject staleness classified by the existing Controlled Renewal rules
remains INVALID evidence / `RENEWAL_REQUIRED` and may coexist with this separate
bounded permission. Any independent blocker continues to block. Permission is
not GREEN PASS, evidence validity or renewal, transition, promotion or closure.
Fresh passing proof remains required at every existing validation, acceptance
and transition boundary. `BOUNDED_INTERMEDIATE_GREEN` in transition mode is
rejected; it is not an acceptance action.

## Material Contract Evolution

UPDATE BY DEFAULT. VERSION WHEN CONTRACT MEANING CHANGES. PRESERVE HISTORY ALWAYS.

IMPLEMENTATION preserves authoritative meaning, consumers and proof obligations.
COMPATIBLE_EVOLUTION preserves existing meaning and evidence eligibility; it
normally remains in-place. CONTRACT_VERSION_CHANGE changes material meaning,
applicability, obligations, proof eligibility or PASS/FAIL and requires explicit
evolution. Ordinary files, tests and refactors are not versioned contracts.

Lean Design C owns this subordinate mechanism; the existing protocol alone owns
Closure. A logical contract is identified by the root of its predecessor chain.
Binding IDs identify stored contract revisions, not duplicated runtime components.
Distinct material revisions use distinct binding and obligation records because
the existing indexes require unique IDs. No version counter or lifecycle engine
is introduced. X2's explicit candidate policy equal to its legacy default is
compatible and stays in-place. Only that documented default is normalized for
coverage; no other material requirement is normalized away.

An existing SUPERSESSION disposition may contain `evolution`, sealed by the
existing PO approval's `disposition_sha256`: SHA256 of UTF-8 JSON, sorted keys,
ensure_ascii=false and separators comma/colon without whitespace. The disposition
contains predecessor/successor binding contract seals, explicit consumer sets,
and complete one-to-one obligation migration. Unsupported split/merge migration
requires a new decision, not inferred mappings. Binding contract seals include
all fields except supersession_ref and the current whole-document authority
digest; requirement defaults are normalized. Obligation seals exclude mutable
status, evidence_refs and disposition_ref. Authority path/heading remains sealed.
Current authority digests still undergo ordinary validation on active contracts.

The approval must be PO-issued for SUPERSESSION, have matching scope, provenance
and an establishment action ID. Its seal binds the exact reviewed disposition.
Established evolution is not reapproved for a consuming action or candidate;
current consequential actions still require the existing separate matched approval.
This uses the existing trusted-caller/review boundary: hashes do not authenticate
authors or protect a coordinated forgery of approvals and dispositions.

The pinned historical Baseline remains unchanged. Historical predecessor contract
content remains equal to its approved coverage; later successor content is sealed
through its PO-approved disposition. Both endpoints must exist. Historical
contracts are reconstructed from preserved records, not reinterpreted against
later authority-document text. Consumer changes and obligation reassignment must
match the approved migration; cycles and self-supersession remain invalid.

Each obligation mapping retains historical_status, historical_evidence_refs,
sealed historical receipt entries in reusable_evidence, an evidence_policy and
a substantive reason. The retained receipt seals apply for every policy; the
field name does not itself authorize reuse. Policy chooses REUSABLE,
RENEWAL_REQUIRED or NOT_APPLICABLE. Only REUSABLE allows the expressly named
predecessor receipts to satisfy a successor, and all ordinary proof checks still
apply under the successor policy. The other policies require independently
associated successor proof when due; they never cancel the successor obligation.
New validated receipts can reference existing artifacts without changing old
receipts or pretending a new external execution occurred. No action-ID-only replay
is inferred. Changed declared evidence dependencies are treated by Controlled
Renewal above, including dependencies outside owning-component paths. Its entry
eligibility and impact-based completion requirements remain distinct. This
approved evolution belongs to the existing Controlled Renewal lifecycle; it
does not create another migration policy, evidence store or closure authority.
Evolution or reassociation alone establishes neither continued applicability
nor permission to activate renewed evidence. Existing migration seals and
ordinary proof checks remain required where applicable.

Predecessor obligations become SUPERSEDED with original evidence references
retained. Successor status uses existing OPEN/CLOSED semantics; evidence never
becomes valid solely through migration. Archive means retained inactive provenance,
not deletion. Same-station Chronicle, Traceability, Current Truth and applicable
checkpoint accounting record the transition and remaining work. Handoff identifies
the active revisions and carried obligations; no new Closure requirement owner
or top-level Gate is introduced.

## Same-Station Decision Persistence

Known material decisions, follow-ups, scope/approval changes, contradictions,
proof and state changes must be classified and persisted at the same station.
Normative decisions go to their Natural Home; required follow-ups to the durable
obligation register; evidence to Traceability and its obligation; historical
events to Chronicle; station state to its single Chronicle block; future
non-current work to the existing Evolution home. No unclassified-outcome registry
is created. The current station records references to classified outcomes.

NO_MATERIAL_OUTCOME is legitimate only without known/observable material changes.
CLASSIFIED_AND_PERSISTED requires existing linked destinations.
UNRESOLVED_CLASSIFICATION blocks station completion/transition. Observable scoped
repository changes augment declared outcomes; unrestricted natural-language
recognition remains model/review dependent and is not called a hard fence.

## Invocation and evidence boundary

`python tools/resolve_authority.py --root . --request REQUEST.json --baseline
BASELINE.json --baseline-sha256 APPROVED_DIGEST` reads only; `--format text`
adds a human-readable context rendering. The JSON request specifies mode
(`resolve`/`transition`), action, scope, station_ref, traceability_ref,
register_ref, current_truth_ref, candidate_sha when applicable, action_id,
paths/observed_changes and optionally expected_snapshot. No credentials belong
in requests, registers or output. The response includes applicable authority,
obligations, station, outcomes, diagnostics and a content snapshot.

For intermediate GREEN requests only, `intermediate_execution` reports action,
action_id, permission and approval_ref. `PERMITTED` authorizes only the matched
bounded implementation action and accompanies `RESOLVED_CONTEXT`; any
`RENEWAL_REQUIRED` diagnostics remain visible. A denied intermediate request
returns `UNRESOLVED` with permission `BLOCKED` and its diagnostics. Ordinary
requests do not acquire intermediate permission semantics.

RESOLVED_CONTEXT is not authorization. TRANSITION_ALLOWED is not Closure PASS.
TRANSITION_BLOCKED and UNRESOLVED prohibit dependent progression. Recheck after
scope, evidence or snapshot changes. Record invocation evidence in Traceability.
CI executes local contracts only; it does not prove real provider/Production
evidence. Evidence receipts and PO records require trusted provenance/review;
hash consistency does not authenticate their author or prove their assertions.
Codex/ChatGPT/future agents consume the same derived context. A disconnected
ChatGPT needs a freshly supplied result. Host interception is not implemented;
hooks are defense in depth, never the sole carrier of obligations.
