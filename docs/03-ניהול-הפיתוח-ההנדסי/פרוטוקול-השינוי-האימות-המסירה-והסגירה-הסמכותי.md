# פרוטוקול השינוי, האימות, המסירה והסגירה הסמכותי

## מעמד

מסמך זה הוא הפרוטוקול הסמכותי היחיד של Stock Sentinel לניהול שינוי מהותי מקצה לקצה.

הוא מחזיק לבדו בסמכות לקבוע ששינוי, ספרינט או שלב רשמי עבר Closure מלא.

כל Gate, Checkpoint, Quality Control, Validation, Review או בקרה אחרת המוזכרים במסמכי המוצר הם בקרות פנימיות של פרוטוקול זה כאשר הם רלוונטיים.

אף בקרה פנימית אינה סמכות Closure עצמאית.

הפרוטוקול הוא כלל ה־Closure הסמכותי הקבוע של Stock Sentinel.

אין ליצור לצדו פרוטוקול Closure עליון מקביל, ואין להחליפו או לבטלו לטובת מנגנון Closure מתחרה.

התפתחות הפרוטוקול נעשית באופן מצטבר באמצעות עדכון, חיזוק, דיוק או התאמה של הבקרות והפרטים הפנימיים שלו כאשר התהליך, הטכנולוגיה, הראיות, הסיכונים או צורכי המוצר מתפתחים.

שינוי בפרט פנימי אינו יוצר כלל סמכותי חדש ואינו מבטל את סמכותו של פרוטוקול זה.

## עיקרון הכלה

הפרוטוקול מכיל את כל דרישות הסגירה השייכות למחזור החיים של שינוי.

כאשר מתגלה בעתיד דרישת בקרה חדשה, Dependency חדש או Escape Path חדש ששייכים להחלטה, מימוש, אימות, מסירה, Production, תיעוד או Closure:

1. מתקנים את הבעיה הקונקרטית.
2. בודקים כיצד היא הצליחה לעבור את מנגנוני הבקרה.
3. מזהים איזה פרט או בקרה פנימית בפרוטוקול דורשים עדכון, חיזוק, דיוק או השלמה.
4. מעדכנים את הפרוטוקול עצמו כאשר הבקרה החדשה שייכת לכלל.
5. הבקרה המעודכנת הופכת לדרישה פנימית מחייבת מכאן והלאה.
6. בודקים שהשינוי מחזק את הכלל הקיים ואינו יוצר מסלול סמכות מקביל או Escape Path חדש.

אין ליצור Gate עליון מקביל.

העיקרון הוא Evolution של אותו כלל סמכותי:
להוסיף, לחזק, לדייק ולהתאים את פרטיו לפי הראיות והצרכים המתפתחים — לא להחליף את מבנה הסמכות שלו בכל פעם שתהליך משנה צורה.

## Natural Homes

הפרוטוקול הוא ה־Orchestrator הסמכותי.

פרטי הבקרות נשמרים בבתי הסמכות הטבעיים שלהם ולא משוכפלים כאן ללא צורך.

דוגמאות:

- החלטות, Impact Map, TDD, Change Control ו־Sprint Governance — ענף 03.
- Quality, Regression ו־Validation — ענף 05.
- Runtime, Deployment, Production Reliability ו־Monitoring — ענף 04.
- Documentation Checkpoint, Current Truth, Chronicle ו־Traceability — ענף 06.
- Product / Architecture controls — בביתם הטבעי בענפים הרלוונטיים.

הפרוטוקול קובע מה חייב לעבור, באיזה סדר, ומה נדרש כראיה לסגירה.

## 1 — Decision Intake

לפני שינוי מהותי:

- מוגדרת הבעיה או המטרה.
- מוגדר ה־Scope.
- מוגדרת התוצאה הנדרשת.
- מוגדרת נקודת היעד שבה התוצאה אמורה להיות נצפית או נצרכת כאשר הדבר רלוונטי.
- מוגדר מי מוסמך להחליט כאשר נדרש אישור בעל המוצר.

## 2 — End-to-End Impact Map

לפני RED, Domain Contract change או שינוי Architecture:

- ממופים Producers.
- ממופים Consumers.
- ממופים Assemblers / Orchestrators.
- ממופים Runtime integration points.
- ממופים Fallbacks.
- ממופות בדיקות.
- ממופים Parallel / Legacy implementations.
- ממופים Branch / CI / Deployment impacts כאשר רלוונטי.
- ממופים Documentation / Current Truth impacts כאשר רלוונטי.
- ממופה נקודת היעד שבה יש להוכיח את התוצאה הסופית של השינוי כאשר קיימת תוצאה נראית למשתמש, למערכת downstream או לתהליך תפעולי.

אין לקבל החלטה מהותית על בסיס ענף חלקי של המערכת.

## 3 — Cross-Check and Decision

כאשר רלוונטי:

- נבדק Normal Case.
- נבדק Failure / Abuse / Operational Risk.
- נבדקת התנהגות Degraded / Fallback כאשר קיימת.
- מתבצעת בדיקה מזווית נוספת.
- מתבצע Benchmark חיצוני מקצועי כאשר הוא יכול לשפר או לאתגר את ההחלטה.
- מוצגת הצעה מנומקת.
- מתקבלת החלטת בעל המוצר כאשר נדרש.

רק לאחר מכן מתחיל המימוש.

## 4 — RED → GREEN → REFACTOR

שינוי התנהגות או Contract מפותח לפי:

RED
→ GREEN
→ REFACTOR

חריג שבו RED חדש אינו הגיוני, כגון Characterization או Regression Guard להתנהגות שכבר נכונה, חייב להיות מוסבר במפורש.

אין ליצור מימוש כוזב רק כדי לייצר RED מלאכותי.

## 5 — Focused Validation

לאחר המימוש:

- מורצות הבדיקות הממוקדות הרלוונטיות.
- נבדקת האינטגרציה הרלוונטית.
- נבדק ה־diff.
- נבדק `git diff --check`.
- נבדקים קבצים לא צפויים ושינויי Scope.

## 6 — Full Regression

לפני Promotion:

- Full Regression עובר.
- אין failure לא מוסבר.
- מספר הבדיקות והתוצאה מתועדים כאשר הם חלק מהראיות לסגירה.

## 7 — Repository and Branch Truth

לפני Commit / Push / Promotion:

- ה־working tree במצב ידוע.
- Branch role נכון ומאושר.
- ה־authoritative local branch נכון.
- Upstream tracking נכון.
- Local HEAD ו־remote authoritative SHA מיושרים כאשר נדרש.
- Default branch role נכון.
- Temporary migration branches או stale local authoritative references אינם נשארים כנתיב בריחה לא־מאומת.
- Destination של Push מאושר.

לאחר Branch Migration יש להוכיח במפורש:

Local authoritative branch
→ upstream
→ remote authoritative branch
→ SHA parity
→ repository cleanliness.

## 8 — Commit and Push

- מבוצע Stage מפורש רק לקבצים הרלוונטיים.
- נבדק staged diff.
- Commit מאושר.
- Push מאושר.
- ה־remote SHA נבדק לאחר Push.

## 9 — CI

כאשר CI רלוונטי:

- CI חייב לפעול על ה־authoritative branch הנכון.
- סביבת CI אינה תלויה ב־Production secrets שלא נדרשים לה.
- Configuration בדיקה לא־סודי ניתן כאשר נדרש.
- CI חייב להשלים בהצלחה על ה־SHA שמיועד לקידום.

Local regression אינו תחליף ל־CI PASS.

## 10 — Promotion and Deployment

Production Deployment חייב להתבסס על מקור הפריסה המאושר.

במצב Production הנוכחי:

- GitHub `main` הוא קו הקוד הסמכותי.
- Railway Production מחובר ל־`main`.
- Auto Deploy פועל.
- Wait for CI פועל.
- Railway GitHub App נשאר מוגבל ל־repository המאושר לפי Least Privilege.

כאשר Wait for CI הוא חלק מה־control plane, יש להוכיח את האכיפה בפועל ולא להסתפק בכך שהמתג מוצג כ־ON.

ההתנהגות הנדרשת:

Push
→ CI running
→ Railway waiting
→ CI PASS
→ Deployment.

## 11 — Exact Deployed Commit Verification

Deployment successful אינו מספיק.

יש להוכיח שה־Production הפעיל מבוסס על ה־commit המדויק שאושר.

כאשר זמין, מאמתים metadata כגון:

- deployed commit SHA;
- deployed branch;
- service;
- environment.

ה־SHA של Production חייב להתאים ל־SHA שאושר במסלול הקידום.

## 12 — Runtime Validation

לאחר Deployment, כאשר רלוונטי, נבדקים בפועל:

- Runtime process.
- Runtime version / toolchain parity.
- Required configuration presence ללא חשיפת Secret values.
- Runtime wiring משמעותי.
- Persistent state.
- Persistent path.
- state continuity across deployment.
- health / operational evidence.

Online או Deployment successful אינם לבדם Runtime Validation.

Runtime wiring מוכח אינו לבדו הוכחה שהתוצאה המוצרית או התפעולית שהשינוי מבטיח אכן מגיעה לנקודת היעד שלה.

## 13 — External Health / Work Evidence

כאשר המערכת תלויה ב־External Lifeguard:

- מאמתים Work Evidence טרי לאחר ה־Deployment.
- מאמתים שהמנטר החיצוני בריא.
- מאמתים שהראיה התקבלה לאחר ה־commit שנפרס.

Configuration presence אינו תחליף ל־End-to-End evidence.

## 14 — Documentation Checkpoint

Documentation Checkpoint הוא בקרה פנימית מחייבת בפרוטוקול זה.

לפני Closure:

1. מבוצע Documentation Impact Map.
2. Current Truth מתעדכן.
3. כל מסמך תחומי שהפך ללא מדויק מתעדכן בביתו הטבעי.
4. Chronicle מתעד Objective, Entry State, Material Changes, Decisions / Rationale, Validation, Exit State ו־Follow-ups.
5. Traceability מחברת החלטות, קוד, בדיקות, Commit / Tag / Version וראיות.
6. Evolution Register מתעד יכולת שעדיין דורשת שדרוג עתידי כאשר רלוונטי.
7. נבדקים כפילויות, סתירות, Placeholder / TODO / TEMPORARY וקישורים שגויים.
8. אין להשאיר החלטה מהותית בזיכרון שיחה בלבד.

Documentation Checkpoint אינו מוסמך לבדו להכריז על Closure.

## 15 — End-to-End Product Outcome Validation

לפני Closure של שינוי שמבטיח Capability, התנהגות או תוצאה נראית למשתמש, למערכת downstream או לתהליך תפעולי, יש להוכיח שהשינוי מספק בפועל את התוצאה שנקבעה ב־Decision Intake בנקודת היעד האמיתית שלה.

כאשר רלוונטי, מסלול ההוכחה חייב לכסות:

Authoritative Input
→ המסלול האמיתי או Production-equivalent המאושר
→ העיבוד וה־Capability החדשים
→ Consumers / Orchestrators הרלוונטיים
→ Final Destination
→ Actual Required Outcome.

הראיה חייבת להוכיח את התוצאה עצמה ולא רק:

- שהרכיב קיים;
- שה־unit tests שלו עברו;
- שהשירות נקרא;
- שה־dependency מוזרק;
- שה־wiring קיים;
- שה־runtime פעיל;
- שה־deployment הצליח;
- או ששני קצוות של השרשרת נבדקו בנפרד.

כאשר קיימת התנהגות Degraded / Fallback מהותית, יש להוכיח גם:

- מהו Success Outcome;
- מהו Degraded / Fallback Outcome;
- כיצד כשל מהותי נעשה גלוי וניתן לחקירה;
- שה־Fallback אינו מציג תוצר ישן, חלקי או מופחת כאילו ה־Capability המלא הצליח, אלא אם התנהגות זו הוגדרה, אושרה ומתועדת במפורש.

כאשר ניתן לבצע הוכחת Production ישירה באופן בטוח וסביר, יש להעדיף אותה.

כאשר Production ישיר אינו בטוח, סביר או דטרמיניסטי מספיק לצורך Closure, נדרשת הוכחת Production-equivalent שמכסה את אותו Contract ואת אותה נקודת יעד, וההגבלה חייבת להיות מתועדת במפורש.

אירוע חי עתידי יכול לשמש Monitoring, Revalidation או ראיה נוספת לאחר Closure, אך אינו יכול להיות הפעם הראשונה שבה מוכח שה־Capability שהוכרז `COMPLETE` אכן מגיע לנקודת היעד שלו.

## 16 — Final Repository Closure

לפני הכרזה `COMPLETE`:

- local authoritative branch נכון.
- upstream נכון.
- local HEAD נכון.
- remote authoritative branch נכון.
- SHA parity מוכח.
- CI PASS מוכח כאשר רלוונטי.
- Production deployed SHA מוכח כאשר רלוונטי.
- Runtime / Health PASS מוכח כאשר רלוונטי.
- End-to-End Product Outcome Validation עבר כאשר רלוונטי.
- Documentation Checkpoint הושלם.
- repository clean.
- אין known open control gap ששייך ל־Scope הסגירה ולא תועד או טופל.

רק לאחר שכל הדרישות הרלוונטיות עברו, ניתן להכריז על Closure.

## 17 — Evidence Rule

טענה אינה PASS רק משום שהמצב "נראה נכון".

כאשר ניתן לקבל ראיה ישירה וסבירה, יש לקבל אותה.

הראיה חייבת להתאים לטענה שאותה היא אמורה להוכיח.

ראיה לכך שרכיב או שלב אחד תקין אינה הוכחה אוטומטית לכך שהשרשרת כולה או התוצאה הסופית תקינות.

דוגמאות:

- Toggle ON אינו הוכחה לאכיפה.
- Deployment successful אינו הוכחת deployed SHA.
- Environment variable PRESENT אינו הוכחת Work Evidence.
- Local tests אינם הוכחת CI.
- Remote `main` נכון אינו הוכחת local branch alignment.
- Component PASS אינו הוכחת End-to-End Product Outcome.
- Runtime wiring PASS אינו הוכחה שהתוכן או התוצאה המובטחים הגיעו ל־Final Destination.

## 18 — Post-Closure Contradiction & Revalidation

Closure הוא קביעה היסטורית המבוססת על הראיות שהיו זמינות ונבדקו בזמן הסגירה.

כאשר לאחר `PASS`, `COMPLETE` או `CLOSED` מתקבלת ראיה חדשה שסותרת באופן מהותי את קביעת הסגירה:

- אין למחוק, לשכתב או להחליף בדיעבד את הקביעה המקורית.
- הקביעה המקורית והראיות ששימשו אותה נשמרות כחלק מה־Audit Trail.
- הסתירה עצמה הופכת לראיה המחייבת Revalidation.

הבדיקה חייבת לשחזר ככל שניתן:

Original Claim
→ Original Acceptance Criteria
→ Original Evidence
→ Tests / Validation Actually Executed
→ Production / Runtime Evidence
→ Changes Since Closure
→ New Contradictory Evidence.

לאחר הבדיקה מסווגים את הממצא כאחת מהאפשרויות:

- `False Closure` — הראיות המקוריות לא הצדיקו את קביעת הסגירה.
- `Regression after valid Closure` — הסגירה הייתה מוצדקת בזמן אמת ושינוי מאוחר יותר פגע בתוצאה.
- `Insufficient Historical Evidence` — אין די ראיות שמאפשרות להכריע באופן אמין בין האפשרויות.

אין לטעון לסיווג שאינו נתמך בראיות.

כאשר ה־Revalidation חושף Escape Path, Dependency או בקרה חסרה:

1. מתקנים את הבעיה הקונקרטית כאשר היא עדיין רלוונטית.
2. מזהים כיצד היא עברה את הבקרות המקוריות.
3. מחזקים את הפרט המתאים בתוך פרוטוקול זה בהתאם לעיקרון ההכלה.
4. מוסיפים Regression / Validation evidence מתאים כאשר נדרש.
5. מעדכנים Current Truth, Chronicle ו־Traceability בהתאם לעובדות החדשות.

Post-Closure Revalidation אינו Gate חדש ואינו Closure Authority מקביל.

הוא מנגנון פנימי של אותו פרוטוקול לשמירת אמינות ה־Closure לאורך זמן.

## 19 — Interaction and Execution Cadence

בעת עבודה פעילה:

- לאחר שלב בטוח שהצליח, הפעולה הבאה ניתנת מיד.
- אין לעצור רק כדי להכריז מה יהיה השלב הבא.
- עצירה מוצדקת רק כאשר הפעולה הבאה תלויה בראיה שעדיין לא התקבלה, בהחלטת בעל המוצר, בסיכון מהותי או באי־ודאות שחייבת להיפתר.
- כאשר נדרשת עצירה לקבלת ראיה, אותה הנחיה חייבת לכלול כבר את הפעולה המדויקת שמפיקה את הראיה.
- במצב של כמה אופציות, מסכמים את החלופות, מנתחים אותן ומביאים אותן להחלטה במקום להפוך את ההתלבטות למנגנון המתנה.

## 20 — Self-Application

שינוי בפרוטוקול עצמו כפוף לפרוטוקול.

כאשר הפרוטוקול נוצר או משתנה באופן מהותי, הוא חייב לעבור את תהליך הסגירה שהוא עצמו מגדיר.

ה־Self-Application חייב לבדוק גם שהשינוי:

- אינו יוצר Closure Authority מקביל;
- אינו מבטל בקרה קיימת ללא החלטה וראיה מפורשות;
- משתלב בסדר ה־End-to-End הקיים;
- מחזק את יכולת הפרוטוקול לזהות ולסגור Escape Paths;
- ואינו מכריז על עצמו כתקין רק משום שהטקסט נראה נכון.

כך הפרוטוקול אינו רק מסמך המתאר Governance — הוא נבחן בפועל על שינויי ה־Governance שלו עצמו.
